# 注意事项

## 提交问题

在对应项目的 Issues 页面反馈问题时，请尽可能附上以下信息，方便维护人员定位：

- 运行环境：操作系统、软件版本和使用的项目分支。
- 报错日志：说明执行的命令，附上完整报错或相关截图。
- 复现步骤：按顺序写出操作过程，并说明预期结果与实际结果。

## Pull Request

- 提交 Pull Request 时，标题应概括本次修改的内容或原因；

- 如果提示存在冲突，必须先解决：先点击个人仓库页面上的 `Sync fork` 按钮同步，再执行 `git pull` 合并最新修改，然后重新提交；


## 代码审核

- 在 `Files changed` 页面按行对 Pull Request 进行评论时，记得点击右上角绿色的 `Submit review`（旧版叫 `Review changes`），选择 `Comment` 后再点击弹窗中的 `Submit review`，否则评论只保存在本地，其他人看不到。
## 提交与合并

- **提交页面的红叉**：如果 `Deploy docs to GitHub Pages` 显示红叉、点开是 `cancelled`，说明这次部署被后一次提交触发的部署取消了（部署组只保留最新一次），修改本身没有失败。以最后一次部署成功、页面内容已更新为准。

- **提交次数**：只有合并进 `master` 的提交才计入；在 PR 里做审核（review）不计入提交次数，但属于参与贡献的一部分。

- **合并节奏**：多个 PR 不要同时合并。合并一个之后，等这次部署跑完，再合并下一个，避免后一次把前一次的部署取消掉。
